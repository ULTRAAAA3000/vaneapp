# Vane Studio (Video Engine) — архитектура и реализация

**Версия документа:** 0.3.0
**Статус:** Этапы 1–2 реализованы: бэкенд, поддомены `post.` / `studio.` и дашборд Studio (загрузка, библиотека, плеер, ключи)
**Источники в документации:** ECONOMY_AND_FINANCE.md §1, §2.5, §2.6, §3, §4.2, §7 · SECURITY_ARCHITECTURE.md §2.2, §3.2 · SOCIAL_PLATFORMS_VERIFICATION.md §5, §7, §8

## 1. Принцип: два независимых продукта на одном аккаунте

Vane Studio — отдельный продукт ($12.00 / мес, ECONOMY §2.5), а не часть постинга (Vane Post). У него свои:

| | Vane Post | Vane Studio |
| :--- | :--- | :--- |
| Дашборд | `post.vaneapp.dev` (`public/app.html`) | `studio.vaneapp.dev` (`public/studio.html`) |
| API дашборда (сессия) | `/api/posts`, `/api/channels`, `/api/keys`… | `/api/video/*` |
| Публичное API (ключи) | `/api/v1/*` · `cpost_live_` / `cpost_test_` | `/api/v1/video/*` · `cvid_live_` / `cvid_test_` |
| Подписка | таблица `subscriptions` (free / api / pro) | таблица `video_subscriptions` |
| Лимит запросов на ключ | 100 / мин | 10 / мин (SECURITY §2.2) |

Общее: аккаунт (`users`) и вход: сессионная cookie выставляется на весь домен `vaneapp.dev`, поэтому один вход действует на обоих поддоменах. Ключ неправильного типа отклоняется мгновенно, до обращения к базе
(`403 wrong_key_scope`, SECURITY §3.2). Бандл Suite ($18.00, §2.6) = подписка Post + подписка Studio: код Studio не зависит от
того, как подписка оплачена, поэтому бандл просто создаст строки в обеих таблицах.

**Связка Studio → Post (ECONOMY §3) работает.** На каждом видео есть кнопка «Announce», а после загрузки (если у аккаунта подключены каналы)
показывается предложение «Announce it in your social channels?». Окно показывает каналы пользователя из Vane Post, черновик текста
(название, начало описания, теги как хэштеги и `{link}`) и предупреждает, когда текст не влезает в лимит выбранной сети.
Сервер записывает пост тем же кодом, что и дашборд Post (`validateCreatePost`, `insertPostGroup`, `countUiPosts`), поэтому лимиты, учёт квоты и доставка совпадают,
а пост уходит в каналы в течение минуты без перехода на `post.vaneapp.dev`. `{link}` заменяется публичной ссылкой на видео; если её нет, она создаётся
в той же транзакции, что и посты (всё или ничего). Если у пользователя нет каналов, окно ведёт в Vane Post. Для этого у Studio есть свои маршруты
(`GET /api/video/announce`, `POST /api/video/videos/:id/announce`), потому что `studio.vaneapp.dev` по замыслу не обслуживает API постинга. Нужна активная Studio.

### Поддомены (`functions/_middleware.ts`, `lib/hosts.ts`, `public/_routes.json`)

Один Pages-проект отвечает на три хоста; продукт выбирается по хосту:

| Хост | `/` | Что отдаёт API |
| :--- | :--- | :--- |
| `post.vaneapp.dev` | дашборд постинга | всё, кроме `/api/video/*` и `/api/v1/video/*` (404) |
| `studio.vaneapp.dev` | дашборд Studio | только `/api/video/*`, `/api/v1/video/*`, `/api/auth/*`, `/api/keys` (остальное 404) |
| `vaneapp.dev`, `www.` | лендинг; `/app` и `/studio` перенаправляют (308) на поддомены | всё (старые интеграции Make / Zapier продолжают работать) |
| localhost, `*.pages.dev` | без изменений: `/app` и `/studio` как обычные пути | всё |

`_routes.json` пропускает через функцию только `/`, `/app`, `/studio` и `/api/*`, поэтому обычные статические файлы её не вызывают.
Проверка: `npm run test:hosts`.

### Каналы публикации (YouTube, TikTok, Instagram Reels): заглушки

В Studio есть раздел «Channels» и окно «Connect a channel», сделанные так же, как в Vane Post. Все три сети пока отмечены «Soon» и не выбираются:
подключение каждой откроется, когда сеть одобрит Vane (SOCIAL_PLATFORMS_VERIFICATION §5, §7, §8: Google brand verification, TikTok Content Posting API review,
Meta business verification). Что уже готово: таблица `video_channels` (токены шифруются так же, как в `channels`), `GET /api/video/channels` (каналы и каталог сетей с флагом `available`),
`POST /api/video/channels/connect` (пока отвечает 409 `platform_unavailable` с причиной) и `DELETE /api/video/channels/:id`. Учётные данные в ответах не возвращаются.

**Как открыть сеть, когда она одобрена:** 1) `available: true` в `lib/videochannels.ts`; 2) добавить в `connectVideoChannel` её вход (OAuth: старт и callback, сохранение
токенов в `video_channels`); 3) в `studio.js` поставить `ready: true` в `VNET` и добавить блок настройки в окно подключения. Список, удаление и сам раздел менять не нужно.
Публикация видео в подключённые сети (кнопка «Publish» на видео, загрузка по resumable API каждой сети) делается следующим шагом после первого одобренного подключения.

### Раздел «API access» (одинаковый в Post и Studio)

В Studio раздел API-ключей сделан так же, как в Post: карточка тарифа и квоты (у Studio это заполненность библиотеки из 90 видео), список ключей
с двухшаговым отзывом, диалог создания ключа (Live / Test, секрет показывается один раз), быстрый старт с готовым `curl`.
Код вынесен в общий модуль `public/assets/apikeys.js`; страница передаёт только своё: что показать в карточке квоты, текст быстрого старта и
область ключей (`scope`). Список ключей запрашивается по области (`GET /api/keys?scope=video`), поэтому ключи `cvid_` и `cpost_` не смешиваются.
У дашборда Post пока своя копия того же кода (`dashboard.js`): перевод его на общий модуль в списке ниже.

### Превью, длина и публичная ссылка

- **Превью и длина.** Браузер при выборе файла сам достаёт кадр (чуть после начала) и длину, а когда загрузка закончена, отправляет кадр:
  `PUT /api/video/videos/:id/thumbnail?d=<мс>&w=<px>&h=<px>` (JPEG до 300 КБ, тип проверяется по байтам). Если браузер не умеет декодировать файл
  (некоторые кодеки), в карточке остаётся заглушка, а загрузка не страдает. Данные лежат в таблице `video_assets`, кадр в R2 рядом с видео.
- **Публичная ссылка.** `POST /api/video/videos/:id/link` создаёт неугадываемый адрес
  `https://studio.vaneapp.dev/api/video/public/<токен 32 символа>` (192 бита случайности); `DELETE` убирает его, и адрес сразу перестаёт работать.
  Одна ссылка на видео (`video_links`, `video_id UNIQUE`), повторный запрос возвращает ту же ссылку, после удаления новая будет другой.
  Открывается без входа, поддерживает Range и HEAD, отдаёт `X-Robots-Tag: noindex`. Создать ссылку можно только при активной Studio, убрать можно всегда.
  Именно такой адрес нужен сетям, которые забирают файл по URL (TikTok, Instagram), и связке «анонс в Post». Через API: `POST|DELETE /api/v1/video/videos/:id/link`
  (тестовый ключ получает ответ нужной формы, ничего не создавая). На `post.vaneapp.dev` эти адреса не обслуживаются.

## 2. Данные (`schema.sql`, только новые таблицы)

- `video_subscriptions` — доступ к Studio. Нет строки = нет доступа; не `active` или истёкший период = нет доступа.
- `videos` — библиотека: одна строка = один файл в R2. Статусы: `uploading` → `ready`, либо `failed` (с причиной в `error`).
- `video_parts` — принятые куски незавершённой загрузки (позволяет докачку). Удаляется при завершении и отмене.
- `video_assets` — превью и длина видео (необязательны). `video_links` — публичная ссылка (одна на видео).
- `video_channels` — подключённые видео-сети (YouTube, TikTok, Instagram); пока пуста.

Файлы лежат в R2-бакете `vane-media` под приватным префиксом `videos/<user id>/<video id>.<mp4|mov>`.
В отличие от медиа постов (`/api/media/:key`, публичные), видео из библиотеки отдаются только владельцу
(`/api/video/videos/:id/file`, с поддержкой Range). Публичные ссылки для сетей, которые забирают файл по URL (TikTok), — отдельный этап.

## 3. Загрузка кусками в R2 (ECONOMY §2.5 «Chunked Resumable Uploads»)

1. `POST /api/video/uploads` — `{ size, contentType, fileName?, title?, description?, tags? }` → `videoId`, `partSize`, `partCount`.
2. `PUT /api/video/uploads/:id/parts/:n` — сырые байты куска `n` (с 1), в любом порядке, повтор безопасен.
3. `GET /api/video/uploads/:id` — какие куски уже приняты (докачка после обрыва).
4. `POST /api/video/uploads/:id/complete` — R2 собирает файл, затем проверка → `ready`. Повторный вызов безопасен.
5. `DELETE /api/video/uploads/:id` — отмена.

Проверки: размер каждого куска ровно `partSize` (правило R2: все куски, кроме последнего, одинаковы), первый кусок — настоящий
MP4/MOV с брендом, совпадающим с заявленным типом; после сборки размер равен заявленному и в файле есть `moov` (проверка
короткими range-чтениями, файл не скачивается). Тип определяется по байтам, не по имени и не по заголовку.
Лимит библиотеки проверяется тем же SQL-запросом, что вставляет строку, поэтому две параллельные загрузки не займут последний слот.
Незавершённая загрузка живёт 24 часа; просроченные удаляются при старте следующей.
