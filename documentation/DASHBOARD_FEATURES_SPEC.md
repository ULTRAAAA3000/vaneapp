# Vane Post — функции дашборда: Календарь и доска, Правила, Ссылки, Библиотека

Спецификация для реализации · 21 октября 2026 · версия 1 (черновик)

## 0. О чём документ

Четыре рабочих раздела дашборда Post. Идея: **автопостинг остаётся центром продукта**, а вокруг него появляется всё, что нужно человеку, чтобы *работать с постами*: готовить, планировать, автоматизировать логику, мерить результат, хранить материалы.

| Модуль | Что делает пользователь | Главная ценность |
|---|---|---|
| **A. Календарь и доска** | Видит все посты по всем сетям в одной сетке, двигает их мышью, ведёт идеи и черновики по стадиям | Ежедневный «домашний» экран |
| **B. Правила** | Собирает «если случилось X, сделай Y» без кода | Автоматизация вокруг поста, а не только времени |
| **C. Ссылки и клики** | Делает короткие ссылки и видит, какой пост и какая сеть привели людей | Настоящая аналитика для всех сетей, включая Telegram |
| **D. Библиотека** | Хранит картинки и тексты, находит и переиспользует их | Меньше рутины, alt-текст и шаблоны всегда под рукой |

**Вне рамок этого документа:** ИИ-функции (есть `AI_FEATURES_SPEC.md`), админка, остальные страницы лендинга, команды и клиенты (будущий тариф Cowork, см. раздел 10).

### Принципы

1. Всё строится на существующей модели: **один пост = одна строка `posts` на канал, строки одной публикации имеют общий `group_id`**.
2. Второй очереди нет. Всё, что уходит в сеть, уходит через воркер по `status = 'scheduled'`.
3. Лимиты тарифов хранятся в `plans.limits` (как `channels`, `postsPerMonth`) и **проверяются на сервере**. Интерфейс только показывает.
4. Новая таблица добавляется в `schema.sql` (идемпотентно). Новая колонка у существующей таблицы добавляется и в `schema.sql` (для новых установок), и отдельным файлом в `migrations/` (для существующей БД). `CREATE TABLE IF NOT EXISTS` колонок не добавляет.
5. Каждое действие, меняющее данные, пишет строку в `logs` (поле `event`), как сейчас.
6. Интерфейс на английском, как весь продукт. Описание здесь на русском.

## 2. Общая часть

### 2.1 Навигация дашборда

Сейчас дашборд Post это одна прокручиваемая страница. Нужна полоса вкладок под шапкой (hash-маршрутизация, как в `admin.js`):

`Create` (текущий экран: редактор, каналы, предпросмотр, список постов) · `Calendar` · `Rules` · `Links` · `Library`

- Вкладка живёт в `location.hash` (`#calendar`), чтобы работали «назад» и ссылки.
- На телефоне полоса вкладок прокручивается горизонтально; календарь по умолчанию открывается списком по дням (сетка месяца на телефоне непригодна).
- Раздел API остаётся там, где он сейчас.
- Каждая вкладка грузит свои данные только при открытии.

### 2.2 Новые ключи лимитов

Добавляются в JSON `plans.limits` и разбираются в `specFromCatalog()` с безопасными значениями по умолчанию, чтобы старые тарифы без этих ключей не сломались. Соглашение «нет ключа = безлимит» или `-1` взять то же, что у `channels` и `postsPerMonth` (проверить в `specFromCatalog`).

| Ключ | Что ограничивает | Free (предложение) | Pro (предложение) |
|---|---|---|---|
| `draftsMax` | Черновиков и идей | 10 | безлимит (жёсткий потолок 500) |
| `rulesMax` | Включённых правил | 3 | безлимит (потолок 50) |
| `linksMax` | Активных коротких ссылок | 20 | безлимит (потолок 5000) |
| `linkHistoryDays` | Глубина статистики кликов | 30 | 365 |
| `storageMb` | Хранилище библиотеки | 100 | 2048 |
| `snippetsMax` | Шаблонов и сниппетов | 10 | безлимит (потолок 300) |

Это стартовые гипотезы: подогнать под реальные расходы (R2 дешёвый, дорогие здесь записи в D1 при кликах, см. C).

Проверка на сервере общим помощником: `assertWithinLimit(env, user, key, currentCount)`. При превышении ответ `402` с понятным текстом и ключом `limit`, чтобы интерфейс показал предложение апгрейда.

### 2.3 Миграции

В `schema.sql` добавляются таблицы `drafts`, `rules`, `rule_runs`, `links`, `link_stats_daily`, `media_assets`, `media_folders`, `snippets` (SQL в модулях ниже).

Новые колонки у **существующей** `posts` (файл `migrations/0002-posts-labels-origin.sql`, добавить `npm run db:migrate:0002`; те же колонки вписать в `CREATE TABLE posts` в `schema.sql`):

```sql
ALTER TABLE posts ADD COLUMN labels         TEXT NOT NULL DEFAULT '[]';  -- JSON: до 3 меток, см. A
ALTER TABLE posts ADD COLUMN origin_rule_id TEXT;                        -- пост создан правилом, см. B
ALTER TABLE posts ADD COLUMN external_meta  TEXT;                        -- JSON: {cid} для Bluesky и т. п., см. B v2
```

`ALTER TABLE ... ADD COLUMN` не идемпотентен, поэтому этот файл применяется **один раз** (так же, как `0001-channel-types.sql`).

### 2.4 Общие технические правила

- **Гонка с воркером.** Любое изменение запланированных постов выполняется условным `UPDATE ... WHERE status = 'scheduled'`; если затронуто меньше строк, чем ожидалось, часть постов уже `processing`. Отвечать частичным успехом (`moved: 2, busy: 1`), не молча.
- **Время.** В БД unix-секунды UTC. Календарь и подписи показываются в часовом поясе браузера; границы дня и недели считает браузер (учёт перехода на летнее время).
- **Прошлое.** Время публикации не раньше, чем `now + 60 с`.
- **Ошибки.** Формат ответа как везде: `{ ok:false, error }`; тексты ошибок такие, чтобы их можно было показать пользователю как есть.
- **Журнал.** События: `draft.create/update/delete`, `post.reschedule`, `post.unschedule`, `post.retry`, `rule.create/update/delete/run`, `link.create/update/delete`, `media.upload/delete`.
- **Приватность.** Ничего из этих модулей не хранит IP и полный User-Agent.

## 3. Модуль A. Календарь и доска

### 3.1 Что видит пользователь

**Вкладка Calendar**
- Переключатель `Month / Week / List`. На телефоне по умолчанию `List` (дни сверху вниз).
- Пост из нескольких каналов показывается **одной плашкой** с точками каналов (как сейчас группируются в списке постов). По клику открывается панель: текст, превью, статус по каждому каналу, действия.
- Цвет плашки зависит от статуса: запланирован, отправляется, опубликован, частично, ошибка. Ошибка и «частично» заметны сразу.
- Перенос: перетащить плашку на другой день. На сенсорном экране и с клавиатуры есть эквивалент: действие **Move…** с выбором даты и времени.
- Клик по пустому дню открывает редактор на вкладке Create с этой датой.
- Фильтры: канал, статус, метка. Справа выдвижная панель **Drafts**: перетащить черновик на день = запланировать (время берётся из «обычного часа» пользователя из Insights, иначе 10:00 по местному).
- В ячейке больше 3 плашек: «+N ещё» открывает список дня.

**Вкладка Calendar → переключатель `Board`** (та же вкладка, другой вид)

Колонки: **Ideas · Drafts · Ready · Scheduled · Published (14 дней) · Needs attention**

- Первые три колонки это `drafts.stage`. Перенос между ними просто меняет стадию.
- `Ready → Scheduled`: открывается выбор даты и времени, затем черновик превращается в запланированные посты.
- `Scheduled → Drafts`: «снять с публикации» (посты возвращаются в черновик, если ни один не в статусе `processing`).
- `Needs attention` содержит ошибки и частичные публикации с кнопками **Retry** и **Edit**.
- Карточка: первые строки текста, значки каналов, метки, дата.

**Метки.** До 3 на пост или черновик, текст до 24 символов, цвет детерминированно считается из текста (таблицы цветов нет). Метки нужны для фильтров и как условие в правилах (B).

**Редактор (вкладка Create).** Кнопка **Save as draft** и автосохранение (задержка 2 секунды) в текущий черновик. Список «Мои черновики» для продолжения работы. При первой загрузке старый `localStorage`-черновик переносится на сервер как черновик стадии `draft`, ключ удаляется.

### 3.2 Данные

Черновики живут в **отдельной таблице**, а не в `posts`, потому что у идеи может не быть каналов.

```sql
CREATE TABLE IF NOT EXISTS drafts (
  id          TEXT    PRIMARY KEY,                              -- uuid
  user_id     TEXT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  content     TEXT    NOT NULL DEFAULT '',
  media_keys  TEXT    NOT NULL DEFAULT '[]',                    -- как в posts
  channel_ids TEXT    NOT NULL DEFAULT '[]',                    -- JSON: куда планировалось, может быть пусто
  stage       TEXT    NOT NULL DEFAULT 'draft',                 -- 'idea' | 'draft' | 'ready' (проверяется в коде)
  labels      TEXT    NOT NULL DEFAULT '[]',
  planned_at  INTEGER,                                          -- желаемая дата, если выбрана (на календаре пунктирная плашка)
  created_at  INTEGER NOT NULL DEFAULT (unixepoch()),
  updated_at  INTEGER NOT NULL DEFAULT (unixepoch())
);
CREATE INDEX IF NOT EXISTS idx_drafts_user ON drafts(user_id, stage, updated_at);
```

Плюс колонка `posts.labels` (раздел 2.3). Метки хранятся JSON-массивом, фильтр делается на клиенте внутри уже загруженного диапазона дат.

### 3.3 API

| Метод и путь | Назначение |
|---|---|
| `GET /api/posts?view=range&from=&to=` | Группы постов за диапазон (максимум 62 дня, до 1000 групп). Возвращает `groups[]` с агрегированным статусом (`scheduled / processing / sent / partial / failed`) и массивом каналов с их статусами и ссылками |
| `GET /api/posts?view=board` | Данные доски: черновики, ближайшие запланированные, отправленные за 14 дней, ошибки за 30 дней |
| `PATCH /api/posts/group/:groupId` | `{ scheduledAt?, content?, mediaUrl?, labels? }`. Меняет только строки со `status='scheduled'`. При смене текста повторяет проверки по сетям (общая функция из `create.ts`). Ответ: `{ moved, busy }` |
| `POST /api/posts/group/:groupId/unschedule` | Только если все строки `scheduled`. Создаёт черновик из группы и отменяет посты **так же, как сейчас работает отмена** (см. «Открытые вопросы», п. 1) |
| `POST /api/posts/:id/retry` | Только для `failed`: статус `scheduled`, `attempts = 0`, время `now + 60 с`. **Квоту повторно не списывает** (пост уже посчитан) |
| `GET/POST /api/drafts`, `PATCH/DELETE /api/drafts/:id` | CRUD черновиков, проверка `draftsMax` |
| `POST /api/drafts/:id/schedule` | `{ scheduledAt, channelIds? }`. Создаёт посты **тем же кодом, что `POST /api/posts`** (те же проверки и тот же `countUiPosts`) и удаляет черновик одной batch-операцией |

Файлы-маршруты: `functions/api/posts/group/[groupId].ts`, `functions/api/drafts/*.ts`; логику вынести в `lib/`, как сделано для `create.ts`.

### 3.4 Крайние случаи

- Часть каналов группы уже отправлена, часть нет. Показывать статус по каждому каналу; перенос затрагивает только неотправленные.
- Канал удалён пользователем. Его посты исчезают каскадом; перед удалением канала предупреждать, сколько постов будет потеряно.
- Квота. Черновики и идеи её не расходуют; она списывается в момент **планирования** (при создании постов).
- Перенос во время отправки. Ответ `busy`, интерфейс объясняет «Этот пост уже отправляется».
- Много постов в одну минуту. Не ограничиваем, но воркер берёт по 20 в минуту; календарь можно предупреждать о «заторе» (больше 20 за минуту), это улучшение для v2.

### 3.5 Критерии готовности

- Перенос плашки на другой день меняет `scheduled_at` у всех неотправленных строк группы и переживает перезагрузку страницы.
- Тот же перенос можно сделать без мыши (действие Move…).
- Черновик без каналов создаётся, сохраняется автоматически и переносится на календарь и в запланированные.
- Превышение `draftsMax` даёт `402` с понятным текстом.
- Старый локальный черновик переносится ровно один раз.
- На телефоне вид List полностью заменяет сетку, горизонтальной прокрутки нет.

## 4. Модуль B. Правила

### 4.1 Идея

«Когда с постом случилось X, сделай Y». Автоматизируется не только время публикации, но и логика вокруг поста. Конструктор без кода: выбрал шаблон, подправил три поля, включил.

**В первой версии только действия, которым не нужны новые возможности сетей** (всё, что воркер уже умеет: опубликовать пост). Удаление и комментарии требуют отдельного кода по каждой сети и вынесены в v2 (раздел 4.6).

### 4.2 Что видит пользователь

**Вкладка Rules**
- Список правил: название, фраза-описание человеческим языком («Когда пост опубликован в Telegram → через 2 ч скопировать в Bluesky»), переключатель вкл/выкл, статус последнего запуска, счётчик запусков.
- **New rule** открывает выбор шаблона, затем форму из трёх шагов: **Когда** (событие, каналы, метка) → **Тогда** (действие и параметры) → **Название**.
- На правиле кнопка **History**: последние 50 запусков со статусом и причиной простым языком («Пропущено: текст 612 знаков, лимит Bluesky 300»).
- Правило, отключённое после повторных ошибок, помечено «Paused after repeated errors».

**Шаблоны v1**

| Шаблон | Событие | Действие |
|---|---|---|
| **Echo to another channel** | пост опубликован в выбранном канале | через N минут опубликовать копию в другом канале |
| **Backup channel** | пост окончательно не отправился (после всех попыток) | сразу отправить копию в запасной канал |
| **Evergreen** | пост опубликован | повторять через N дней, до K раз |

### 4.3 Модель правил

**События (триггеры) v1:** `post.published`, `post.failed` (названия совпадают с событиями вебхуков). `post.failed` срабатывает только после исчерпания попыток (`MAX_ATTEMPTS`), то есть через некоторое время после первой неудачи.

**Условия v1:** каналы-источники (пусто = любой), метка поста (из модуля A). Больше условий не нужно, чтобы форма оставалась простой.

**Действия v1:**

| Действие | Параметры | Что происходит |
|---|---|---|
| `copy_to` | `targetChannelIds`, `delayMinutes` (0 до 10080), `onTooLong: 'skip' \| 'truncate'` | Создаёт новый пост с тем же текстом и медиа в других каналах. Для `post.failed` это шаблон Backup channel |
| `requeue` | `everyDays` (1 до 365), `times` (1 до 12), `targetChannelIds` (по умолчанию тот же канал), `jitterMinutes` (0 до 120) | Публикует тот же материал снова через N дней, K раз. Небольшой случайный сдвиг, чтобы повторы не выглядели механически |

**Защита от петель.** Правила **никогда не срабатывают на постах с `origin_rule_id`** (то есть на постах, созданных правилами). Поэтому пара «Telegram → Bluesky» и «Bluesky → Telegram» не будет перекидывать пост бесконечно, а Evergreen не запускает Echo на своих повторах. Действие `copy_to` не может быть направлено в тот же канал-источник.

### 4.4 Данные

```sql
CREATE TABLE IF NOT EXISTS rules (
  id                 TEXT    PRIMARY KEY,                       -- uuid
  user_id            TEXT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name               TEXT    NOT NULL,
  enabled            INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0, 1)),
  trigger_event      TEXT    NOT NULL,                          -- 'post.published' | 'post.failed' (проверяется в коде)
  source_channel_ids TEXT    NOT NULL DEFAULT '[]',             -- JSON; пусто = любой канал
  label              TEXT,                                      -- условие: пост содержит эту метку
  action             TEXT    NOT NULL,                          -- 'copy_to' | 'requeue' (в v2 добавятся другие; без CHECK, чтобы не пересоздавать таблицу)
  params             TEXT    NOT NULL DEFAULT '{}',             -- JSON с параметрами действия
  fail_streak        INTEGER NOT NULL DEFAULT 0,                -- подряд неудачных запусков
  last_run_at        INTEGER,
  runs_total         INTEGER NOT NULL DEFAULT 0,
  created_at         INTEGER NOT NULL DEFAULT (unixepoch()),
  updated_at         INTEGER NOT NULL DEFAULT (unixepoch())
);
CREATE INDEX IF NOT EXISTS idx_rules_user ON rules(user_id, enabled);

CREATE TABLE IF NOT EXISTS rule_runs (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  rule_id         TEXT    NOT NULL REFERENCES rules(id) ON DELETE CASCADE,
  user_id         TEXT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  source_post_id  TEXT    NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  occurrence      INTEGER NOT NULL DEFAULT 1,                   -- номер повтора для requeue
  run_at          INTEGER NOT NULL,
  status          TEXT    NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending', 'done', 'skipped', 'failed')),
  result          TEXT,                                         -- причина простым языком
  created_post_id TEXT,
  created_at      INTEGER NOT NULL DEFAULT (unixepoch()),
  updated_at      INTEGER NOT NULL DEFAULT (unixepoch()),
  UNIQUE (rule_id, source_post_id, occurrence)                  -- один запуск не создаётся дважды
);
CREATE INDEX IF NOT EXISTS idx_rule_runs_due ON rule_runs(status, run_at);
CREATE INDEX IF NOT EXISTS idx_rule_runs_rule ON rule_runs(rule_id, created_at);
```

Плюс колонка `posts.origin_rule_id` (раздел 2.3). Старые запуски чистятся ежедневно (оставляем 30 дней), как делается для `webhook_deliveries`.

### 4.5 Как это работает внутри

1. **Постановка в очередь.** В `finish()` (`worker/src/dispatch.ts`), рядом с `enqueueWebhookEvent`, вызывается `enqueueRuleRuns(env, post, event)`: выбирает включённые правила пользователя, подходящие по событию, каналу и метке, и делает `INSERT OR IGNORE` в `rule_runs` с `run_at = now + delay`. Посты с `origin_rule_id` пропускаются.
2. **Исполнение.** Новая функция `runDueRules(env, now)` (`functions/api/lib/rules.ts`) вызывается из `scheduled()` в `worker/src/index.ts`, по тому же шаблону, что `deliverDueWebhooks` (в `waitUntil` с перехватом ошибок, чтобы сбой правил не мешал публикации). Берёт до 20 запусков `pending` с `run_at <= now`.
3. **Действие `copy_to`.** Читает исходный пост, проверяет, что он не отменён, проверяет лимиты целевых сетей **той же общей функцией, что и создание поста**, и создаёт посты с новым `group_id` и `origin_rule_id`. Расписание: `max(now + 60 с, run_at)`.
4. **Действие `requeue`.** Создаёт пост (`occurrence = k`), и если `k < times`, добавляет запуск `k + 1` со сдвигом `everyDays` дней относительно **времени созданного поста**.
5. **Квота.** Посты, созданные правилами, **считаются как обычные** (`countUiPosts`). Если квота исчерпана и перерасход отключён, запуск получает `skipped` с причиной «Monthly post limit reached».
6. **Самозащита.** Три предохранителя:
   - не больше `rulesMax` включённых правил на пользователя;
   - не больше 300 запусков в сутки на пользователя (жёсткий потолок, не зависит от тарифа);
   - после 5 подряд неудачных запусков (`failed`, не `skipped`) правило выключается, причина пишется в историю.

### 4.6 Версия 2: действия, требующие нового кода в сетях

| Действие | Что нужно сделать |
|---|---|
| `delete_after` (удалить пост через N часов) | Telegram `deleteMessage` (нужны `chat_id` из учётных данных канала и `message_id`; **у Telegram есть ограничение по возрасту сообщения, проверить актуальные условия до обещания пользователям**), Bluesky `com.atproto.repo.deleteRecord` (rkey из `uri`), Mastodon `DELETE /api/v1/statuses/:id` (id достать из сохранённого URL или лучше сохранять отдельно). LinkedIn и Threads: проверить возможности их API |
| `first_comment` (ответить на свой пост, например, со ссылкой) | Bluesky: для ответа нужны `uri` **и `cid`** родителя; воркер сегодня сохраняет только `uri`, поэтому сохранять `cid` в `posts.external_meta` при публикации (createRecord его возвращает). Mastodon: `in_reply_to_id`. Telegram-каналы: комментарии живут в связанной группе обсуждений, поддерживаем только если она настроена, иначе действие недоступно |
| `notify` (уведомить меня) | Появляется вместе с каналом уведомлений (например, личные сообщения от бота с привязкой аккаунта). Без него действие бессмысленно, поэтому в v1 его нет |

Для v2 нужна **таблица возможностей сетей** (`network × действие → поддерживается / ограничения`), на её основе форма правил скрывает недоступные комбинации.

### 4.7 API

`GET/POST /api/rules` · `PATCH/DELETE /api/rules/:id` · `GET /api/rules/:id/runs`. В публичный `v1` API не выносим.

### 4.8 Критерии готовности

- Echo: пост опубликован в Telegram, через заданное время в Bluesky появляется копия с `origin_rule_id`, и она не запускает других правил.
- Один и тот же исходный пост не даёт двух запусков одного правила (проверка по `UNIQUE`).
- Если текст не помещается в целевую сеть и выбрано `skip`, в истории видна причина с цифрами.
- Исчерпанная квота не приводит к ошибке воркера, а даёт `skipped`.
- Evergreen K раз с интервалом N дней создаёт ровно K повторов и останавливается.
- Правило с 5 ошибками подряд выключается и показывает причину.
- Отмена исходного поста до запуска даёт `skipped`, а не публикацию.

## 5. Модуль C. Ссылки и клики

### 5.1 Идея

Короткие ссылки с UTM и счётчиком кликов. Это единственный способ получить **честную аналитику для Telegram**, где через Bot API статистики, насколько известно, почти нет (перепроверить актуальную документацию): клики считаются на вашем редиректе. Ключевая фишка: **отдельная ссылка на каждый канал**, поэтому видно, какая сеть привела людей, а не только «сколько всего».

### 5.2 Что видит пользователь

**Вкладка Links**
- Таблица: короткая ссылка (копировать), куда ведёт, клики за 7 и 30 дней, мини-график, метка и источник (создана вручную или из поста).
- **New link**: адрес, название, UTM-поля (по желанию), срок действия (v2), свой код (платно). Сразу показывается QR-код.
- Карточка ссылки: график по дням (30/90/365, в пределах `linkHistoryDays`), разбивка по каналам (для ссылок из постов), по странам, по источникам перехода, по типу устройства. Выгрузка CSV (Pro).
- Отключить ссылку: переходы дают страницу «Эта ссылка отключена».

**В редакторе постов**
- Переключатель **Track link clicks** (по умолчанию включён, если в тексте есть ссылка). До трёх адресов на пост.
- Для каждого канала создаётся **своя** короткая ссылка с `utm_source=<сеть>`, и в текст именно этого канала подставляется она. Предпросмотр показывает уже итоговый текст.
- В списке постов и в календаре у поста появляется счётчик кликов.
- Карточка Insights получает показатель Clicks (7 дней).

### 5.3 Данные

```sql
CREATE TABLE IF NOT EXISTS links (
  id            TEXT    PRIMARY KEY,                         -- uuid
  user_id       TEXT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  code          TEXT    NOT NULL UNIQUE,                     -- короткий код в адресе, 7 символов base62
  target_url    TEXT    NOT NULL,                            -- уже с UTM, если они заданы
  label         TEXT,
  post_group_id TEXT,                                        -- если создана из поста
  channel_type  TEXT,                                        -- для какой сети (атрибуция)
  clicks_total  INTEGER NOT NULL DEFAULT 0,
  last_click_at INTEGER,
  is_active     INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0, 1)),
  expires_at    INTEGER,
  created_at    INTEGER NOT NULL DEFAULT (unixepoch())
);
CREATE INDEX IF NOT EXISTS idx_links_user  ON links(user_id, created_at);
CREATE INDEX IF NOT EXISTS idx_links_group ON links(post_group_id);

CREATE TABLE IF NOT EXISTS link_stats_daily (
  link_id TEXT    NOT NULL REFERENCES links(id) ON DELETE CASCADE,
  day     TEXT    NOT NULL,                                  -- 'YYYY-MM-DD', UTC
  dim     TEXT    NOT NULL,                                  -- 'all' | 'country:UA' | 'ref:t.me' | 'dev:mobile'
  clicks  INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (link_id, day, dim)
);
```

Сырые клики **не храним**: только ежедневные счётчики (это и приватность, и экономия записей). IP и User-Agent не сохраняются.

### 5.4 Редирект

- Маршрут `functions/l/[code].ts` на основном домене: `https://vaneapp.dev/l/<code>`. Добавить `/l/*` в `public/_routes.json` (иначе функция не вызовется) и пропустить в `_middleware.ts` для всех хостов.
- Ответ **302** (не 301): ссылку можно отключить или изменить, и браузеры не закешируют. Заголовки `Cache-Control: private, max-age=0`.
- Подсчёт выполняется в `ctx.waitUntil(...)` (UPSERT в `link_stats_daily`: строка `all` и до трёх измерений), чтобы не задерживать пользователя. Цель: серверное время меньше 50 мс.
- Страна из `request.cf.country`, источник это только хост из `Referer`, устройство определяется грубо по User-Agent (mobile/desktop).
- **Боты не считаются.** Предпросмотры ссылок в Telegram, Bluesky, Mastodon, Facebook, X, Slack, Discord, LinkedIn и WhatsApp сами ходят по ссылке и раздули бы счётчик. Фильтр по User-Agent (`TelegramBot`, `Twitterbot`, `facebookexternalhit`, `Slackbot`, `Discordbot`, `LinkedInBot`, `WhatsApp`, `Mastodon`, `bsky`, общее `bot|crawler|spider|preview`) и запросы `HEAD`. Боту редирект отдаётся как обычно, чтобы карточка предпросмотра строилась по целевой странице.
- Неизвестный код даёт 404, отключённая или истёкшая ссылка даёт 410 с понятной страницей.

### 5.5 Защита от злоупотреблений (это сокращатель, значит вектор фишинга)

- Создавать могут только вошедшие пользователи с подтверждённым e-mail.
- Целевой адрес: только `http(s)`, длина до 2000, без логина и пароля в адресе, не ссылка на `/l/` (без петель), без известных чужих сокращателей (чтобы не делать цепочки).
- Зарезервированные коды (`api`, `app`, `admin`, `login`…) и стоп-слова. Лимит создания в час на пользователя.
- Эндпоинт жалобы `POST /api/links/report` (публичный, с rate limit). Возможность отключить ссылку по коду нужна в админке (делаешь сам): флаг `is_active = 0` уже есть.
- Опционально при создании проверять адрес через Google Safe Browsing (нужен ключ API).

### 5.6 API

`GET/POST /api/links` · `PATCH/DELETE /api/links/:id` · `GET /api/links/:id/stats?days=` · `GET /api/links/export.csv` (Pro).
Из редактора: `POST /api/posts` принимает `trackLinks: true`, и создаются связанные ссылки в той же batch-операции, что и посты.

### 5.7 Масштабирование

Каждый клик это 2 до 4 записей в D1. Для старта нормально. Если кликов станет много, счётчики переносятся в Cloudflare Workers Analytics Engine (`writeDataPoint` и SQL API для чтения), структура ответов API при этом не меняется. Чистка `link_stats_daily` старше окна `linkHistoryDays` выполняется ежедневно воркером (по аналогии с `purgeOldWebhookDeliveries`).

### 5.8 Критерии готовности

- Переход по `/l/<code>` отдаёт 302 на целевой адрес и увеличивает счётчик на 1; запрос бота предпросмотра счётчик не увеличивает.
- Пост в три канала с одной ссылкой даёт три разные короткие ссылки и три строки в разбивке по каналам.
- Отключённая ссылка даёт 410 и не считается.
- Статистика старше `linkHistoryDays` недоступна через API.
- Страница политики конфиденциальности обновлена: какие данные считаются (страна, источник, устройство, без IP).
- Создание ссылки на `javascript:`, на `localhost` и на саму себя отклоняется.

## 6. Модуль D. Библиотека

### 6.1 Идея

Место, где живут материалы пользователя: картинки и тексты. Сегодня загруженный файл не оставляет записи в БД (`media/upload.ts` кладёт его в R2 и отдаёт ссылку), поэтому увидеть, переиспользовать или удалить его нельзя. Библиотека это исправляет и заодно даёт **alt-текст** и **шаблоны**.

### Статус реализации

**Шаг 1 (готов):** таблица `media_assets`; каждая загрузка из редактора и из вкладки записывается; полоса вкладок **Create / Library**; вкладка Library со списком (по 60), фильтром по типу, поиском по имени, загрузкой, копированием ссылки и удалением в два клика; защита от удаления файла из неотправленного поста; лимит `storageMb` (действует только при включённом переключателе `enforce_limits`, как лимит каналов; нет ключа = без ограничений).

**Шаг 2 (готов):** выбор файла из библиотеки в редакторе (ссылка «or choose from your library» под зоной загрузки открывает диалог с фильтром, поиском и списком; файл прикрепляется без повторной загрузки и ведёт себя как загруженный); создание поста со ссылкой на уже удалённый файл отклоняется общей проверкой `validateCreatePost` (то есть и в публичном API).

Отличия от плана ниже: удаление сразу и окончательно (не мягкое); превью не создаются, в сетке показывается сам файл с ленивой загрузкой; колонки `alt_text`, `folder_id`, `tags`, `sha256`, `thumb_key`, `used_count`, `last_used_at` в таблице уже есть, но пока не используются.

**Не сделано:** alt-текст в публикации, папки и теги, превью, защита от дублей, шаблоны текстов, обрезка, импорт. Файлы, загруженные до появления таблицы, в библиотеке не видны и в квоту не входят (разовый перенос из R2 по метаданным `userId` можно сделать отдельной задачей).

### 6.2 Что видит пользователь

**Вкладка Library** с двумя разделами: **Media** и **Texts**.

**Media**
- Сетка превью (2 колонки на телефоне), поиск по имени, тегам и alt-тексту, фильтры «картинки / видео / неиспользованные».
- Загрузка перетаскиванием, сразу несколько файлов, с индикатором.
- Папки (плоские, без вложенности), теги, массовые действия: переместить, тегнуть, удалить.
- На карточке: название, размер, размеры в пикселях, **alt-текст**, бейдж «Используется в N постах».
- Шкала занятого места: «Использовано 48 МБ из 100 МБ».

### 6.4 Логика

- **Одна точка записи.** Существующий `POST /api/media/upload` после успешной загрузки тоже создаёт строку в `media_assets` (чтобы всё, что загружено из редактора, появлялось в библиотеке). Для вкладки Library добавляется `POST /api/library/upload` (multipart: `file` и `thumb`), который использует **те же проверки**: реальный тип по байтам, размеры, потолки 5 МБ для картинок и 20 МБ для видео, лимит загрузок в час.
- **Дубли.** Браузер считает SHA-256 до загрузки. Если такой файл уже есть, сервер возвращает существующий (`duplicate: true`) и ничего не грузит.
- **Превью.** Генерируются в браузере (canvas, WebP 400 px) и грузятся вместе с файлом. Обработки картинок на сервере нет.
- **Квота.** `storageMb` считается как сумма `size_bytes` всех записей пользователя; проверка при загрузке, ответ `402`. Как и лимит каналов, действует только при включённом `enforce_limits`.
- **Удаление.** Сразу и окончательно (строка и объект в R2). **Воркер скачивает файл из R2 в момент отправки**, поэтому файл, на который ссылается запланированный или отправляемый пост, удалять нельзя: ответ `409`. Для уже отправленных постов файл не нужен (сети хранят свою копию), но превью такого поста в списке постов перестанет показываться. Когда появятся черновики, их ссылки на файлы нужно учесть в той же проверке.
- **Учёт использования.** При создании поста или черновика с медиа счётчик `used_count` и `last_used_at` обновляются в той же batch-операции.
- **Alt-текст до публикации.** Сегодня элемент `media_keys` это только строка. Расширяем формат: допускается объект `{ "key": "...", "alt": "..." }`, строка продолжает работать. Обновить `resolveMediaUrl` и `mediaOf` в `dispatch.ts`; в Bluesky alt уходит в `alt` у изображения, в Mastodon в `description` медиа. Публичный `v1` API остаётся со строкой `mediaUrl`.
- **Один файл на пост.** Это текущее ограничение, библиотека его не меняет (несколько картинок в посте это отдельная задача).
- **Шаблоны.** Подстановка переменных только в браузере; сервер хранит текст как есть. Лимит `snippetsMax`.

### 6.5 API

`GET /api/library/assets?q=&kind=&folder=&unused=1&cursor=` · `POST /api/library/upload` · `PATCH /api/library/assets/:id` (имя, alt, теги, папка) · `DELETE /api/library/assets/:id` · `POST /api/library/assets/bulk` (теги, перенос, удаление) · CRUD для `/api/library/folders` и `/api/library/snippets` · `GET /api/library/usage` (занято и лимит).

### 6.6 Версия 2

- **Обрезка под сети** (1:1, 4:5, 16:9, 1.91:1, 9:16) в браузере; результат сохраняется как новая запись с тем же alt-текстом.
- **Импорт старых постов** из Bluesky (`app.bsky.feed.getAuthorFeed`) и Mastodon (список постов аккаунта). **Из Telegram импорт невозможен**: Bot API не отдаёт историю канала, известны только посты, отправленные через Vane. Отдельная таблица (чтобы не путаться с квотой и очередью):

```sql
CREATE TABLE IF NOT EXISTS imported_posts (
  id          TEXT    PRIMARY KEY,
  user_id     TEXT    NOT NULL REFERENCES users(id)    ON DELETE CASCADE,
  channel_id  TEXT    NOT NULL REFERENCES channels(id) ON DELETE CASCADE,
  external_id TEXT    NOT NULL,
  content     TEXT    NOT NULL,
  media_urls  TEXT    NOT NULL DEFAULT '[]',
  url         TEXT,
  posted_at   INTEGER NOT NULL,
  created_at  INTEGER NOT NULL DEFAULT (unixepoch()),
  UNIQUE (channel_id, external_id)
);
CREATE INDEX IF NOT EXISTS idx_imported_user ON imported_posts(user_id, posted_at);
```
  Раздел **My posts** показывает отправленные через Vane и импортированные, действие **Reuse** открывает текст в редакторе (в коде уже есть `reusePost`). Импорт идёт кусками из воркера, не больше 200 постов на канал.
- **Удаление данных GPS из фото** без перекодирования (вырезание блока EXIF из JPEG в браузере) с включённым по умолчанию переключателем. Это забота о приватности, о которой пользователи редко вспоминают сами.
- Автоудаление неиспользуемых файлов старше N дней (опция).

### 6.7 Критерии готовности

- Файл, загруженный из редактора, появляется в библиотеке.
- Повторная загрузка того же файла не занимает места и возвращает существующую запись.
- Удаление файла, используемого запланированным постом, отклоняется с перечнем постов.
- Превышение `storageMb` даёт `402`; шкала занятого места совпадает с суммой.
- Alt-текст, выбранный в библиотеке, доходит до Bluesky и Mastodon (проверить на реальных аккаунтах).
- Старые посты со строковым `media_keys` продолжают отправляться без изменений.
- Шаблон со `{date}` и `{weekday}` подставляет значения по дате публикации.

## 7. Free, Pro и отдельные платные продукты

Все числа это **стартовые гипотезы**, подогнать после первых данных. Дорогое место здесь одно: **записи в D1 при кликах** (C). R2 стоит копейки, поэтому хранилище можно делать щедрым.

| Модуль | Free | Pro | Отдельный платный продукт |
|---|---|---|---|
| **A. Календарь и доска** | Календарь во всех видах, доска, метки, 10 черновиков | Безлимитные черновики | — |
| **B. Правила** | 3 правила, все шаблоны v1 | До 50 правил; действия v2 (удаление, первый комментарий) | — |

## 8. Порядок работ

Зависимости: B опирается на метки из A и на общую функцию создания постов; C и D независимы; alt-текст из D затрагивает пайплайн публикации.

| Фаза | Что | Грубая оценка* |
|---|---|---|
| **0. Фундамент** | Вкладки и hash-маршрут, разбор новых лимитов и `assertWithinLimit`, миграция `0002`, обновление README и этого документа | 2–3 дня |
| **1. A** | Черновики, календарь (месяц/неделя/список), доска, перенос, повтор отправки, метки, перенос локального черновика | 6–9 дней |
| **2. B v1** | Таблицы, постановка и исполнение запусков, три шаблона, история | 8–12 дней |
| **3. C** | Редирект, фильтр ботов, список и карточка ссылок, `trackLinks` в редакторе, политика конфиденциальности | 6–9 дней |
| **4. D v1** | Таблицы, загрузка и квота, сетка и выбор в редакторе, alt-текст в пайплайне, шаблоны | 7–10 дней |
| **5. v2** | Действия удаления и комментариев (с таблицей возможностей сетей), обрезка, импорт, GPS-очистка, Analytics Engine при необходимости | по необходимости |

\* Дни чистой разработки одним разработчиком, без согласований и ожидания API. Это ориентир, а не обещание.

**Что не делаем в этой версии:** ИИ-функции, несколько медиа в одном посте, правку уже опубликованных постов, публичный API для правил и ссылок, свой домен для ссылок, команды и клиентов.

## 9. Открытые вопросы и риски

1. **Квота при отмене.** Как `cancel.ts` сегодня обращается со счётчиком (возвращает ли единицу)? Действие «снять с публикации» должно вести себя точно так же. Проверить до реализации A.
2. **Домен ссылок.** Для старта `vaneapp.dev/l/<код>`: проще и без риска, что новый домен попадёт в спам-списки сетей. Отдельный короткий домен возможен позже.
3. **Где считать клики.** D1 достаточно на старте; порог перехода на Analytics Engine определить по нагрузке.
4. **Ограничения сетей для v2.** Условия удаления сообщений в Telegram и комментарии в каналах нужно перепроверить по актуальной документации перед тем, как обещать эти действия.
5. **`external_meta` лучше начать заполнять сразу** (в фазе 1): `cid` для Bluesky и числовой id для Mastodon. Это дешёвая страховка для действий v2, потом восстанавливать эти данные по старым постам трудно.
6. **Лимиты 5 и 20 МБ** связаны с тем, что Telegram скачивает медиа по ссылке. Библиотека их не меняет; снять можно загрузкой в Telegram напрямую, это отдельная задача.
7. **Юридическое.** Обновить политику конфиденциальности и условия: клики (страна, источник, устройство), хранение файлов, жалобы на ссылки.
8. **Пропускная способность воркера.** 20 постов в минуту. Правила, массовый перенос и календарные «заторы» могут упираться в это; следить и при необходимости поднять `BATCH_SIZE` с учётом лимитов подзапросов Workers.
9. **Смена часового пояса пользователя.** Посты хранятся в UTC и не сдвигаются, но подписи в календаре поменяются; показывать выбранный пояс рядом с календарём.
10. **Антизлоупотребления в ссылках** (5.5) нужны до публичного запуска C, а не после.

## 10. Задел под тариф Cowork (команды и клиенты)

Сейчас не реализуем, но и не должны закрыть себе дорогу:

- Все новые таблицы привязаны к `user_id`. Для Cowork к `posts`, `drafts`, `rules`, `links`, `media_assets`, `snippets` добавляется `workspace_id` (nullable, миграцией), а квоты и индексы считаются на рабочее пространство.
- `drafts.stage` без `CHECK`, а колонки доски строятся из списка констант, поэтому стадии `in_review` и `approved` добавятся без перестройки таблицы.
- Согласование клиентом по ссылке без регистрации это отдельная сущность (например, `approval_links`), к модулям этого документа она не привязывается.
- Роли (`owner / editor / viewer`) и журнал правок появятся вместе с рабочими пространствами; уже сейчас каждое действие пишется в `logs` с `user_id`.
